# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Frontend (run from repo root, package manager is `pnpm`):

- `pnpm dev` — Vite dev server on port 3000
- `pnpm build` — production build
- `pnpm preview` — preview the production build
- `pnpm test` — run Vitest once (`vitest run`). For watch mode use `pnpm exec vitest`; for a single file `pnpm exec vitest path/to/file.test.ts`
- `pnpm lint` — ESLint
- `pnpm format` — Prettier write
- `pnpm typecheck` — `tsc --noEmit`

Supabase local dev (the `supabase` CLI is a devDependency, so use `pnpm exec supabase ...`):

- `pnpm exec supabase start` — bring up the local stack (Postgres, Auth, Studio, Mailpit, etc.) using `supabase/supabase/config.toml`. **Run from inside `supabase/`**, not the repo root — from the root the CLI derives a different project id (`open_board` instead of `supabase`) and won't find the running containers (`supabase_*_supabase`).
- `pnpm exec supabase stop` / `pnpm exec supabase status`
- `pnpm exec supabase db reset` — drop, re-run migrations from `supabase/supabase/migrations/`, then apply `supabase/supabase/seed.sql`
- After any migration change: `cd supabase && pnpm exec supabase db reset && pnpm exec supabase gen types typescript --local > ../src/lib/types/supabase.ts`
- Default ports: API/Kong `54321`, Postgres `54322`, Studio `54323`, **Mailpit web UI `54324`**, Analytics `54327`. All emails GoTrue sends (signup, password recovery, magic links, email change) land in Mailpit at http://localhost:54324.
- Frontend env vars (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) come from `supabase status` output; `APP_URL` is the app's own origin, used for auth email redirect links.
- Direct SQL access for debugging: `psql postgresql://postgres:postgres@127.0.0.1:54322/postgres`

The `supabase/` directory **also** contains a vendored copy of the upstream self-hosted docker-compose tree (`supabase/docker-compose.yml`, `supabase/dev/`, `supabase/.env`, `supabase/utils/*.sh`). That is **not** what the dev workflow uses — it's a separate self-host reference, kept here for production deployment scenarios. Don't run it alongside `supabase start`; the port maps will clash.

## Architecture

**TanStack Start** (SSR React framework built on Vite + Nitro) with **self-hosted Supabase** as the backend. There is no separate backend service in this repo — server-side logic lives inside the TanStack Start app as server functions that call Supabase.

### Frontend (`src/`)

- **Routing**: file-based via `@tanstack/react-router`. Route files live in `src/routes/`; `src/routeTree.gen.ts` is auto-generated by the router plugin — never edit it. Layout routes use a `route.tsx` file (e.g. `routes/auth/route.tsx` wraps everything under `/auth`). `__root.tsx` is the root layout and owns `<ThemeProvider>` and devtools.
- **Router bootstrap**: `src/router.tsx` builds a `QueryClient` and wires `setupRouterSsrQueryIntegration`, so React Query state is hydrated across SSR boundaries. Route loaders/components can use the `queryClient` from route context.
- **Server functions**: created with `createServerFn` from `@tanstack/react-start` (see `src/lib/server-functions/auth.ts`). They run on the server, validate input via `.inputValidator(zodSchema)`, and are called from the client like async functions (`useMutation({ mutationFn: loginFunc })` passes `{ data: value }`).
- **Supabase clients** (two today, a third planned):
  - `getSupabaseServerClient()` (`src/lib/utils/supabase.ts`) — per-request `createServerClient` (`@supabase/ssr`) reading/writing cookies through TanStack Start's `getCookies` / `setCookie`. This is the default client for all data access; it runs as the signed-in user and RLS applies. It is a **factory, not a singleton** — call it inside each server-function handler (a module-scope client would leak auth state across concurrent requests).
  - `getSupabaseAdminClient()` (`src/lib/utils/supabase-admin.ts`) — service-role client that **bypasses RLS**. Import only from server-function modules, never from anything reachable by client code, and always check the caller's permissions before using it. Legitimate uses: pre-auth reads (e.g. `auth_settings.enable_registration` during registration), user invites/administration.
  - A browser-side client is planned **only** for Supabase Realtime subscriptions (Phase 5 of the roadmap); all mutations stay in server functions.
- **Auth/session pattern**: `__root.tsx` `beforeLoad` calls `getUserFunc` (GET server fn wrapping `supabase.auth.getUser()` + `get_user_permission_paths` RPC) and returns `{ user, permissions }` into router context. Route guards live in `beforeLoad`s: `routes/index.tsx` redirects unauthenticated users to `/auth/login`; `routes/auth/route.tsx` redirects authenticated users away from auth pages (except `/auth/reset-password`, where the recovery-code exchange signs the user in mid-flow). After login/logout, call `router.invalidate()` to re-run `beforeLoad`s and refresh the context.
- **Password reset flow**: the recovery email links to `/auth/reset-password?code=...`; the route's `beforeLoad` exchanges the one-time code for a session via `exchangeCodeFunc`, then redirects to the clean URL (so refreshes don't re-consume the code). Invalid/expired codes redirect with `?invalid=true`.
- **Forms**: `@tanstack/react-form-start` with Zod validators in `src/lib/validators/`. Pattern: declare a validator once and pass it as both `onMount` and `onChange` to keep submit state in sync.
- **Generated DB types**: `src/lib/types/supabase.ts` is the generated Supabase schema — treat as generated, regenerate via Supabase CLI rather than editing.
- **Theme**: `ThemeProvider` (`src/components/theme-provider.tsx`) stores `light`/`dark`/`system` in `localStorage` and injects an inline `<ScriptOnce>` (`getThemeScript`) to set the class before hydration to prevent flash.
- **UI**: shadcn/ui configured via `components.json` with the `base-luma` style, `neutral` base color, and **HugeIcons** as the icon library (`@hugeicons/react` + `@hugeicons/core-free-icons`) — not Lucide. Add components with `npx shadcn@latest add <name>`; they land in `src/components/ui/`. The `cn` util lives at `@/lib/utils/cn` (not `@/lib/utils`).

### Application layers (clean architecture)

Dependencies point one way: routes → components/hooks → server functions → Supabase. Data fetching never lives in components; Supabase clients are never touched outside `src/lib/server-functions/`.

- `src/routes/**` — composition only: `beforeLoad` guards, loaders, page assembly. No fetch logic or business rules.
- `src/components/<feature>/` — feature/presentational components (receive data via props or hooks).
- `src/components/ui/` — shadcn/reUI primitives only; add via CLI, don't hand-write business logic here.
- `src/lib/hooks/` — the only place `useQuery`/`useMutation` wrap server functions, so caching/invalidation lives in one layer.
- `src/lib/server-functions/` — one module per entity: `createServerFn` + `.inputValidator(zod)` + permission check + Supabase call. Errors: `setResponseStatus(4xx)` then `throw`.
- `src/lib/validators/` — Zod schemas shared by forms (client) and server functions (server); single source of truth for shapes.
- `src/lib/utils/` — pure utilities and the Supabase client factories.
- `src/lib/types/` — domain types + generated `supabase.ts`.

### Database / RBAC model

Schema lives in `supabase/supabase/migrations/`. Core kanban tables (`workspaces → boards → lists → cards`, plus `labels`, `check_list_items`, `comments`, `card_activities`, attachments) and an RBAC layer (`roles`, `permissions` (path strings like `board:create`), `role_permissions`, `user_roles`, per-resource `workspace_permissions`/`board_permissions`). RLS is enabled on every table.

- Permission checks in SQL: `check_permissions(VARIADIC paths)` (true if the user holds any of the paths or `auth:superuser`), `check_workspace_permissions(id)` / `check_board_permissions(id)` (public resource, owner, superuser, or granted per-resource permission), `check_card_access(id)`. The frontend reads the user's paths via the `get_user_permission_paths()` RPC.
- The `workspaces`/`boards` **select** policies check `user_id = auth.uid()` directly on the row (not only via the `check_*` functions) — required for `INSERT ... RETURNING` to see the just-inserted row; don't "simplify" that away.
- Auth settings: `auth_settings` (singleton, `id = 1`) holds `enable_registration`; `default_roles` holds the roles granted to new users, scoped by `type` enum (`global`, `public_registration`, `private_registration`, `sso_provider` + `provider` column). The `handle_new_user` trigger creates the profile row and assigns matching default roles (invited users are detected via `invited_at`).
- Inserts into `workspaces`/`boards` must set `user_id` explicitly to `auth.uid()` — the insert policies require it and the columns have no default.
- Seed (`supabase/supabase/seed.sql`): permissions, roles `superuser`/`user`/`admin`, storage buckets, and the `user` role as a `global` default role.

### Path aliases (tsconfig)

- `@/*` → `src/*`
- `@components/*` → `src/components/*`
- `@lib/*` → `src/lib/*`

Both `@/components/...` and `@components/...` resolve. Existing code mixes them — prefer the scoped aliases (`@components`, `@lib`) for new code in `src/`.

### Supabase directory (`supabase/`)

Two layouts live side-by-side here — don't confuse them:

1. **`supabase/supabase/` — the live local-dev config** managed by the Supabase CLI.
   - `config.toml` — single source of truth for ports, services, auth providers, mailer, etc. The `[inbucket]` section is the mailer; the CLI keeps the legacy name but the actual image is Mailpit.
   - `migrations/` — SQL migrations applied by `supabase db reset` / `supabase db push`
   - `seed.sql` — dev seed
   - `snippets/` — saved Studio SQL snippets

2. **`supabase/` (top level) — vendored self-hosted docker-compose**, mirrored from `supabase/supabase` upstream as a reference for production self-hosting. Files: `docker-compose.yml`, `dev/docker-compose.dev.yml`, `utils/*.sh`, `tests/*.sh`, `CHANGELOG.md`, `versions.md`. Update by syncing from upstream rather than hand-editing. `supabase/volumes/` is gitignored and only created if you actually run this stack.

## Conventions

### ESLint vs Prettier conflict (important)

The two tools disagree and **ESLint is the source of truth** — actual committed code follows ESLint:

| | Prettier (`.prettierrc`) | ESLint (`eslint.config.js`) | Code follows |
|---|---|---|---|
| Semicolons | `semi: false` | `@stylistic/semi: always` | **semicolons** |
| JS string quotes | `singleQuote: false` (double) | `@stylistic/quotes: single` | **single** |
| JSX attribute quotes | (default double) | `@stylistic/jsx-quotes: prefer-double` | **double** |

Do **not** run `pnpm format` blindly across the codebase — it will introduce lint errors. Use `pnpm lint --fix` for autofixable style. If you must run Prettier, restrict it to files you know are safe (e.g. JSON, CSS — the prettier plugin in use is `prettier-plugin-tailwindcss` for class sorting).

Other ESLint rules worth knowing:
- `@stylistic/jsx-self-closing-comp` is enforced for both components and html — write `<div />` not `<div></div>` for empty elements.

### TypeScript

- Strict mode plus `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noUncheckedSideEffectImports`, `verbatimModuleSyntax` — use `import type` for type-only imports.
- `tsconfig.json` excludes `supabase/` and ESLint ignores `supabase/**` plus the generated `src/lib/types/supabase.ts` and `src/routeTree.gen.ts` — the vendored self-host tree contains Deno code that must not be typechecked with the app.
- React 19 + the new JSX transform (`jsx: react-jsx`); don't import `React` just for JSX.
